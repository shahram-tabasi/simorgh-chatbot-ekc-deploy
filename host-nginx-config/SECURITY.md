# دسترسی از اینترنت به شبکه‌ی داخلی — سند امنیتی

سرور `simorghai` (`192.168.1.68`) دروازه‌ی بین اینترنت و شبکه‌ی داخلی است. این سند
می‌گوید آن دروازه چطور کار می‌کند، چه چیزی از بیرون باز است، چه چیزی نیست، و کدام
تغییرات می‌توانند این محافظت را **بی‌صدا** از کار بیندازند.

مخاطب این سند مدیر IT است. متن فارسی است چون خواننده‌اش فارسی‌زبان است؛ دستورها و
نام تنظیمات انگلیسی مانده‌اند چون عیناً همان چیزی‌اند که در فایل‌ها نوشته شده.

پیاده‌سازی در `host-nginx-config/default.conf` است و همان فایل روی سرور در
`/etc/nginx/conf.d/default.conf` می‌نشیند. این سند جایگزین خواندن آن فایل نیست؛
می‌گوید چرا آن‌طور نوشته شده.

آخرین تأیید عملی: **۲۶ شهریور ۱۴۰۵ (2026-09-17)**، از یک سرور خارج از شبکه.

---

## ۱. مسیر یک درخواست

```
کاربر اینترنت
   │
   │  DNS عمومی: zone simorghai.com روی ArvanCDN
   ▼
لبه‌ی ArvanCDN  (185.143.233.238 / 185.143.234.238)
   │  TLS اینجا terminate می‌شود، بعد دوباره با HTTPS به مبدأ
   ▼
فایروال  95.38.203.173 : 443  ──DNAT──▶  192.168.1.68 : 443
   │
   ▼
nginx روی 192.168.1.68
   │  ① این کلاینت داخلی است یا بیرونی؟
   │  ② این نام اجازه‌ی انتشار دارد؟
   │
   ├─ سرویس‌های روی همین سرور  ──▶  127.0.0.1 (upstream ثابت)
   │
   └─ سرویس‌های کلاستر  ──PDNS 192.168.1.68──▶  192.168.1.2xx
```

کاربر داخل شبکه همان مسیر را بدون اروان و بدون فایروال طی می‌کند: مستقیم به
`192.168.1.68`.

نکته‌ی تعیین‌کننده: **مسیریابی بر اساس نام دامنه (Host) انجام می‌شود، نه پورت.**
همه‌ی این سرویس‌ها پشت یک پورت واحد (443) روی یک IP واحد نشسته‌اند. همین موضوع،
ریسک اصلی این معماری را می‌سازد.

## ۲. ریسک اصلی: مسیریابی بر اساس Host آدرسی ندارد که فایروال شود

وقتی سرویسی روی پورت اختصاصی خودش باشد، بستنش با فایروال ساده است. اینجا این‌طور
نیست. به محض اینکه پورت 443 عمومی به این nginx برسد، **هر کسی در اینترنت می‌تواند
هر نامی از zone داخلی را درخواست کند**، فقط با ست کردن هدر `Host`:

```bash
curl --resolve monitoring.simorghai.com:443:95.38.203.173 \
     https://monitoring.simorghai.com/
```

این دستور **به هیچ رکورد DNS عمومی نیاز ندارد**. یعنی اگر تنها کنترل ما این بود که
«رکورد عمومی نساز»، انتشار یک ساب‌دامین عملاً کل zone داخلی را منتشر می‌کرد:
مانیتورینگ، لاگ‌ها، OpenStack، رجیستری.

> **از این یک جمله در کل سند مهم‌تر چیزی نیست:**
> نساختن رکورد DNS، یک کنترل امنیتی **نیست**. فقط مخفی‌کاری است.

## ۳. راه‌حل: فهرست انتشار صریح

nginx قبل از اینکه چیزی را proxy کند دو سؤال می‌پرسد. هر دو در بالای
`default.conf` تعریف شده‌اند.

**سؤال اول — این کلاینت داخلی است؟**

```nginx
geo $realip_remote_addr $client_is_internal {
    default        0;
    127.0.0.0/8    1;
    10.0.0.0/8     1;
    172.16.0.0/12  1;
    192.168.0.0/16 1;
}
```

**سؤال دوم — این نام اجازه‌ی انتشار دارد؟**

```nginx
map $host $host_is_public {
    default  0;          # هر نامی که اینجا نیامده باشد: فقط داخلی
    cloud.simorghai.com  1;
    ...
}
```

**و تصمیم:**

```nginx
map "$client_is_internal$host_is_public" $simorghai_allowed {
    "00"    0;   # کلاینت بیرونی + نام منتشرنشده = تنها حالت رد
    default 1;
}
```

هر vhost مربوط به `simorghai.com` این نگهبان را در **سطح server** دارد، نه داخل یک
`location` — پس هر مسیری را در آن vhost می‌پوشاند، از جمله مسیرهایی که بعداً اضافه
شوند:

```nginx
if ($simorghai_allowed = 0) {
    return 404;
}
```

**چرا `404` و نه `403`؟** جوابی که بگوید «این هست ولی اجازه نداری» برای کسی که
دارد اسکن می‌کند، یک سرویس کشف نام است. `404` چیزی لو نمی‌دهد.

این نگهبان روی نُه vhost فعال است و از بیرون تست شده: همه‌ی نام‌های منتشرنشده
`404` می‌دهند.

## ۴. حمله‌ی دوم: جعل هویت از پشت CDN

این یکی ظریف است و اگر پیدا نمی‌شد، کل فهرست انتشار را بی‌اثر می‌کرد.

ترافیک عمومی از لبه‌ی اروان می‌آید، پس آدرسی که nginx می‌بیند مال اروان است نه
بازدیدکننده. راه‌حل استاندارد این است که رنج‌های CDN را trust کنیم و آدرس واقعی را
از هدر `X-Forwarded-For` بخوانیم (فایل `arvan-real-ip.conf`).

اما ماژول `realip` وقتی این کار را می‌کند، **مقدار `$remote_addr` را بازنویسی
می‌کند**. و نگهبان ما اگر روی `$remote_addr` بنا شده بود، این اتفاق می‌افتاد:

```
کلاینت مهاجم → CDN → nginx
هدر ارسالی:  X-Forwarded-For: 192.168.1.50
نتیجه:       $remote_addr = 192.168.1.50  →  geo می‌گوید «داخلی»
دسترسی:      monitoring، logs، openstack — همه باز
```

این سناریو **اندازه‌گیری شد، نه حدس زده شد**: با trust بودن CDN، یک هدر جعلی
بررسی مبتنی بر `$remote_addr` را به «داخلی» برگرداند، در حالی که بررسی مبتنی بر
`$realip_remote_addr` روی «خارجی» ماند.

**راه‌حل:** نگهبان روی `$realip_remote_addr` بنا شده — آدرس واقعی طرف مقابلِ
اتصال TCP. هیچ هدری آن را تکان نمی‌دهد.

یک اثر جانبی که باید بدانید: کاربر داخلی که از مسیر CDN وارد شود (بیرون و برگشت)،
«خارجی» حساب می‌شود. که در آن لحظه واقعاً هست.

## ۵. حلقه‌ی proxy

بلوک wildcard نام درخواستی را از PDNS resolve می‌کند و به `https://$host` وصل
می‌شود. اگر رکوردی به `192.168.1.68` اشاره کند، nginx به خودش وصل می‌شود و این
زنجیره تمامی ندارد.

یک نگهبان دوم این اشتباه را به یک خطای واضح تبدیل می‌کند:

```nginx
if ($http_x_simorgh_proxy) {
    return 508 "Proxy loop: ...";
}
```

nginx روی درخواست‌های خروجی خودش یک نشانه می‌گذارد؛ اگر همان نشانه برگردد، یعنی
حلقه. به‌جای طوفان بی‌پایان درخواست، یک `508` با پیام روشن.

**پیامد عملی:** سرویسی که روی خود `192.168.1.68` اجرا می‌شود، با رکورد PDNS
قابل سرویس‌دهی نیست. این سرویس‌ها (Design Suite، chatbot، GitLab، Kibana، KARA،
DEMO) هرکدام یک بلوک اختصاصی با upstream ثابت به `127.0.0.1` دارند. سرویس جدید از
این نوع، یک بار نیاز به نوشتن بلوک دارد.

## ۷. آنچه این سیستم محافظت **نمی‌کند**

این بخش مهم‌ترین قسمت سند است. فهرست انتشار مرز مشخصی دارد و بیرون آن مرز، چیزهایی
هست که باید جداگانه دیده شوند.

**۱) مسیرهای path-based روی `simorghai.electrokavir.com`.**
همان اپ‌ها عمداً و به‌صورت عمومی زیر دامنه‌ی دیگری هم سرو می‌شوند:

```
simorghai.electrokavir.com/simorgh-design-suite/
simorghai.electrokavir.com/chatbot/
simorghai.electrokavir.com/eplanix/
simorghai.electrokavir.com/gitlab/
simorghai.electrokavir.com/kibana/
simorghai.electrokavir.com/kara/
simorghai.electrokavir.com/demo/
```

این vhost نگهبان ندارد — طراحی‌اش این است که عمومی باشد. پس `0` گذاشتن روی
`gitlab.simorghai.com` **گیت‌لب را از اینترنت برنمی‌دارد**؛ فقط می‌گوید ساب‌دامین
راه دوم ورود نیست. برای بستن کامل یک اپ، باید `location` مربوطه در vhost
الکتروکویر هم حذف یا محدود شود.

**۲) رجیستری روی سرور عمومی.**
`registry.simorghai.com` در PDNS به `5.161.149.228` اشاره می‌کند — یک سرور Hetzner
روی اینترنت که مستقیم جواب می‌دهد. سوییچ `0` فقط جلوی عبور از این nginx را می‌گیرد؛
روی دسترسی مستقیم به آن سرور هیچ اثری ندارد. محافظت از آن باید روی خود Hetzner
انجام شود. (`harbor.` یک CNAME به همین است.)

**۳) دور زدن CDN.**
`simorghai.electrokavir.com` مستقیم به `95.38.203.173` اشاره می‌کند، پس IP مبدأ
عملاً عمومی است. هر کسی می‌تواند اروان را دور بزند و مستقیم به مبدأ وصل شود.
نگهبان جلوی نام‌های منتشرنشده را می‌گیرد، ولی سرویس‌های منتشرشده از مسیر مستقیم هم
در دسترس‌اند و سپر DDoS اروان روی آن‌ها اعمال نمی‌شود. قفل کردن 443 به رنج اروان
ممکن نیست، چون همان پورت به الکتروکویر هم سرویس می‌دهد.

**۴) احراز هویت خود اپ‌ها.**
این nginx فقط تصمیم می‌گیرد چه کسی به **درِ** یک سرویس برسد. اینکه پشت آن در لاگین
لازم است یا نه، کار خود اپ است. تا پیش از این، شبکه‌ی داخلی خودش یک لایه‌ی محافظت
بود؛ برای هر سرویسی که به `1` تغییر می‌کند، باید جداگانه تأیید شود که احراز هویت
اجباری دارد. **به‌ویژه chatbot:** اگر ورودی‌اش باز باشد، هر کسی می‌تواند از منابع
محاسباتی LLM محلی استفاده کند.

**۵) هر چیزی که HTTP نیست.**
TURN، مدیای UDP جیتسی، و هر سرویس TCP خام از این پروکسی رد نمی‌شوند. اگر از بیرون
لازم‌اند، مسیر جداگانه و تصمیم امنیتی جداگانه می‌خواهند.

## ۸. رویه‌ی باز یا بستن یک سرویس

**برای باز کردن یک سرویس روی اینترنت:**

۱. تأیید کنید که خود اپ احراز هویت اجباری دارد.
۲. در `default.conf`، در `map $host $host_is_public` مقدار را `1` کنید.
۳. دیپلوی:
   ```bash
   cd /home/ubuntu/simorgh-chatbot-ekc-deploy && git pull
   sudo cp host-nginx-config/default.conf /etc/nginx/conf.d/default.conf
   sudo nginx -t && sudo systemctl reload nginx
   ```
۴. در پنل اروان رکورد `A` با مقدار `95.38.203.173` و ابر روشن بسازید.
۵. با بخش ۹ تأیید کنید.

**برای بستن:** مقدار را `0` کنید و reload بزنید. حذف رکورد DNS **کافی نیست** و
حتی لازم هم نیست — سوییچ است که تصمیم می‌گیرد.

**نکته‌ی نام‌ها:** فهرست انتشار روی **نامی که کلاینت درخواست کرده** کار می‌کند، نه
روی vhostای که در نهایت سرویس می‌دهد. یک vhost با دو نام (مثل `chatbot.` و
`chat.`) به **دو ردیف** در فهرست نیاز دارد.

## ۹. تست‌های تأیید

بعد از هر تغییر در فهرست انتشار، قوانین NAT فایروال، یا رنج‌های trust شده‌ی CDN،
این دو تست را از یک سرور **خارج از شبکه** اجرا کنید.

**نام منتشرنشده باید رد شود** — این تست DNS را عمداً دور می‌زند، دقیقاً همان کاری
که یک مهاجم می‌کند:

```bash
curl -sk -o /dev/null -w "%{http_code}\n" \
  --resolve monitoring.simorghai.com:443:95.38.203.173 \
  https://monitoring.simorghai.com/
# انتظار: 404
```

**نام منتشرشده باید کار کند:**

```bash
curl -sI https://cloud.simorghai.com/ | head -1
# انتظار: 302 (ریدایرکت لاگین Nextcloud)
```

اگر تست اول `404` نداد، یعنی نگهبان از کار افتاده. **این وضعیت اضطراری است** —
بخش ۱۰ را ببینید.

> تست از داخل شبکه بی‌فایده است: از داخل همه‌چیز باز است و هر دو تست پاس می‌شوند
> حتی اگر نگهبان کاملاً خراب باشد.

## ۱۰. تغییراتی که این محافظت را بی‌صدا می‌شکنند

هر سه مورد زیر باعث می‌شوند چیزی به‌ظاهر خراب نشود، در حالی که مرز امنیتی از بین
رفته است. بعد از هرکدام، حتماً تست بخش ۹ اجرا شود.

| تغییر | چه اتفاقی می‌افتد |
|---|---|
| اضافه شدن SNAT/masquerade به مسیر فایروال | همه‌ی کلاینت‌ها «داخلی» دیده می‌شوند و کل فهرست انتشار بی‌اثر می‌شود |
| رنج بیش‌ازحد باز در `arvan-real-ip.conf` (خصوصاً `0.0.0.0/0`) | هر کلاینتی می‌تواند آدرس خودش را جعل کند |
| ساختن رکورد wildcard `*` در zone عمومی اروان | نقشه‌ی کامل شبکه‌ی داخلی با یک brute-force ساده‌ی DNS قابل استخراج می‌شود، حتی وقتی درخواست‌ها `404` می‌گیرند |

اسکریپت `update-arvan-ips.sh` عمداً هیچ URL پیش‌فرضی ندارد و ورودی نامعتبر یا
`0.0.0.0/0` را رد می‌کند — چون لیست اشتباه در آن فایل یعنی nginx به هدر جعلی
اعتماد کند.
